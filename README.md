# UFC Fight Predictor

Predicts UFC fight outcomes using a gradient-boosted model trained on historical fight data — from scraping raw stats off UFCStats to serving win-probability predictions with per-fight explanations through a web app.

## What it does

Given two fighters, the model outputs a win probability for each, along with the top features (via SHAP) that drove that specific prediction. The whole system is a pipeline: scrape → engineer features → train → serve.

## Problem it solves

Fight outcomes aren't well captured by simple win/loss records — quality of opposition, current form, and stylistic matchups all matter. This project builds a feature set that captures fighter skill over time (via Elo and rolling stats) and matchup dynamics (via differential features), then uses that to make a leakage-free, explainable prediction.

## Architecture

```
UFCStats.com → Scraper (SQLite) → Feature Engineering (CSV) → Model Training (XGBoost) → API (FastAPI) → Frontend (React)
```

### 1. Scraper (`scrapers/ufcstats_scraper.py`)
- `requests` + `BeautifulSoup`, crawls events → fights → fighter pages
- Stores into a normalized SQLite schema: `events`, `fighters`, `fights`, `rounds`
- Resumable — tracks what's already scraped, safe to re-run
- Handles two different table layouts UFCStats has used over time

### 2. Feature Engineering (`scrapers/feature_engineering.py`)
- **Elo ratings** — updated fight-by-fight, computed strictly in chronological order so no future data leaks into a fighter's pre-fight rating
- **Rolling stats** — last-3/last-5 fight averages for striking, takedowns, control time, etc.
- **Differential features** — `diff_*` = fighter A's stat minus fighter B's, since the gap between fighters matters more than either absolute value
- **Composite scores** — hand-built `striking_score` and `grappling_score` blending accuracy, volume, and defense
- **Side randomization** — ~50% of rows have fighter A/B swapped, to prevent the model from learning UFCStats' fixed listing order as a shortcut
- All normalization constants are computed using only past data, to avoid leakage

### 3. Model Training (`models/train.py`)
- **XGBoost** classifier
- **Walk-forward validation** — train on all data before year Y, test on year Y, repeated across years — respects the time-series nature of fight data instead of random splitting
- **Optuna** (TPE sampler) tunes 9 hyperparameters, with the objective averaged across walk-forward folds rather than a single split
- **SHAP** (`TreeExplainer`) for both global feature importance and per-prediction explanations

### 4. API (`api/main.py`)
- **FastAPI**, model + artifacts loaded once at startup
- `/predict` — takes two fighter IDs, rebuilds the same feature vector used in training, returns win probabilities and SHAP-based explanation
- `/fighters`, `/fighter/{id}/stats` — search and lookup endpoints

### 5. Frontend (`frontend/`)
- React + Vite
- Fighter search, probability display, and a SHAP explanation chart per prediction

## Tuned hyperparameters

Optuna searches over:

| Parameter | Range |
|---|---|
| `n_estimators` | 100–400 |
| `max_depth` | 2–6 |
| `learning_rate` | 0.01–0.3 (log scale) |
| `subsample` | 0.5–1.0 |
| `colsample_bytree` | 0.5–1.0 |
| `min_child_weight` | 1–10 |
| `gamma` | 0.0–5.0 |
| `reg_alpha` | 0.0–2.0 |
| `reg_lambda` | 0.0–2.0 |

## Setup

```bash
pip install -r requirements.txt

# 1. Scrape data
python scrapers/ufcstats_scraper.py

# 2. Build features
python scrapers/feature_engineering.py

# 3. Train the model
python models/train.py

# 4. Run the API
uvicorn api.main:app --reload

# 5. Run the frontend
cd frontend && npm install && npm run dev
```

## Known limitations

- `lightgbm` and `mlflow` are listed in `requirements.txt` but not currently used anywhere in the codebase
- Model artifacts (`models/artifacts/`) are not committed to this repo and must be generated by running `train.py`
- Deployment is not yet finalized

## Results

- ~7,000+ historical bouts
- ~68% prediction accuracy on walk-forward validation
